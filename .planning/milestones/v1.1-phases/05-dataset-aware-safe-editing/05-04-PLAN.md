<objective>
Build the host-side `AuthoringGate` (the async buffer-then-apply confirm gate) and the `fixAll` host-side rule runner — the two orchestration seams that turn classification + snapshot + safety-level into the actual SAFE-03/04/05 behavior.

Purpose: The central architecture finding (RESEARCH, HIGH confidence) is that the interceptor fires SYNCHRONOUSLY inside the facade, but SAFE-03/04 need an ASYNC confirm before geometry touches the editor. Making the facade async is the explicit anti-pattern (it ripples through run_code's sync replay, primitives, MutationResult, the A3 test). The gate therefore lives ONE LAYER UP at the chat apply path, which is already async (store.ts:1710-1722). The gate snapshots the bound dataset, dry-runs the proposed mutation against a clone, classifies add/modify/delete via `classifyMutation`, and — per the persisted `safetyLevel` — either applies immediately (pure-add or Level 3) or buffers and awaits an Apply/Cancel decision (Levels 1-2 for destructive ops). Separately, SAFE-05 requires "fix all" to iterate `editor.getAllFeatures()` (the canonical id-keyed set), never the model's compacted `sampleIds` view, so out-of-context features are not silently skipped. This phase lands the host-side rule-runner SEAM + one proof; the model-facing bulk tool is Phase 6 (TOOLS-02).

Output: `createAuthoringGate(editor, { getSafetyLevel, emitDiffBlock })` with a `review(...)`/apply orchestration, and a pure `fixAll` rule runner with a proof test. The Apply/Cancel UI and chat-loop wiring land in Plan 05; this plan ships the gate logic against an injectable decision callback so it is headlessly testable.

Depends on Plan 01 (`classifyMutation`, modify/delete verbs), Plan 02 (`DatasetSnapshotManager` + the editor's snapshot accessor), Plan 03 (`safetyLevel`).
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| AI proposal → editor apply | The gate IS this boundary: nothing destructive crosses it without classification + (per level) confirmation, and every apply is snapshotted. |
| Model's compacted view → "fix all" scope | The model only sees sampled ids; a rule must be evaluated host-side over the full set, never over the model's list. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-15 | Tampering / Repudiation | a destructive AI edit applied without user awareness | mitigate | The gate buffers modify/delete under Level 1-2 and awaits Apply/Cancel; even Level 3 snapshots + emits the diff (D-07/D-12) so the action is visible and reversible. |
| T-05-16 | Tampering (silent partial apply) | "fix all" skipping out-of-context features | mitigate | `fixAll` iterates `editor.getAllFeatures()`; the model supplies the rule, not the feature list (SAFE-05 / Pitfall 2 / A3). Proof test asserts an out-of-sample feature is modified. |
| T-05-17 | Elevation of Privilege | the gate bypassing the interceptor on apply | mitigate | The real apply always routes through `createAuthoring`/the Plan-01 verbs → `runInterceptors`; the gate never calls `editor.*` directly. |
| T-05-18 | Tampering | Cancel leaving partial state | mitigate | Cancel discards the buffered mutation with zero editor mutation (asserted); the dry-run runs against a clone, never the real editor. |
| T-05-19 | Repudiation | an apply that cannot be undone | mitigate | The gate pushes a `DatasetSnapshotManager` snapshot before every apply (one per apply unit, D-11) so SAFE-06 undo covers it. |
</threat_model>
