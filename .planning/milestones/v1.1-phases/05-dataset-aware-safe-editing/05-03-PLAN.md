<objective>
Persist the configurable safety level through the Phase-1 encrypted settings store (SAFE-04) and build the pure binding resolver that powers the binding chip (SAFE-01) — the two state mechanisms the gate and UI consume.

Purpose: SAFE-04 requires a safety level (1 = preview + confirm all / 2 = confirm destructive only, default / 3 = trust + undo) that persists; D-09 mandates it ride the existing encrypt-to-self settings envelope (inheriting NIP-46 async signer handling, version migration, account-swap guards) rather than a bespoke localStorage key. SAFE-01 requires the chat to be explicitly bound to a target dataset, always visible: D-01 auto-binds to the open draft/dataset, D-02 auto-creates-and-binds an untitled draft when nothing is bound (binding is created and shown before the mutation — never refusal), D-03 surfaces the bound dataset's identity (name / unsaved-draft / feature count).

Output: a `safetyLevel` field on `ChatSettingsSnapshot` (default 2) with migration default + round-trip persistence, a `setSafetyLevel` store action, `buildSnapshot` carrying the field, and a pure `binding.ts` resolver returning the bound identity + an auto-create-and-bind signal.

This plan touches chat settings + a new `safeEditing/binding.ts` only. It shares `store.ts` with Plan 05 (chat-loop wiring), so Plan 05 is sequenced to a later wave; within Wave 1 this plan owns the `ChatSettingsSnapshot` interface change.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| Decrypted settings envelope → in-memory store | A tampered/future/garbage envelope must not crash the load or inject an out-of-range safetyLevel; migration validates every field. |
| Editor store → binding resolver | The resolver is read-only over editor identity; it must never refuse a mutation (D-02) or expose anything beyond name/unsaved/featureCount. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-05-11 | Tampering | a tampered envelope sets an out-of-range `safetyLevel` (e.g. 0/5) to weaken gating | mitigate | `migrateV1ToV2` membership-checks `safetyLevel` and falls back to 2 (the safe default) on any invalid value; never trusts the decrypted shape (WR-03 idiom). |
| T-05-12 | Denial of Service (data loss appearance) | garbage envelope throws during decrypt/migrate → looks like settings loss | mitigate | Migration never throws on garbage (existing T-01-04 invariant, extended for safetyLevel); failed decrypt surfaces the existing visible failed state, not silent default. |
| T-05-13 | Information Disclosure | safetyLevel persistence leaking secrets into serialized state | accept | safetyLevel is a non-secret integer riding the same encrypt-to-self envelope; the Phase-1 secret-exclusion partialize is unchanged (no apiKey added). |
| T-05-14 | Tampering / Repudiation | the gate firing on an unbound target (no visible anchor) | mitigate | The binding resolver always yields a shown target or an auto-create-and-bind signal (D-02) — no mutation path lacks a visible binding; enforced end-to-end in Plan 04/05. |
</threat_model>
