<objective>
Close the Phase-7 UAT BLOCKER: invoking `optimize_geometry` on a real oversized dataset
crashes the app. The root cause is already DIAGNOSED and EMPIRICALLY CONFIRMED — do NOT
re-investigate. Two compounding defects must both be fixed:

1. `optimize()` is QUADRATIC in per-feature vertex count (per-iteration `turf.kinks`
   topology validation over the full set + `turf.simplify({highQuality:true})` × MAX_ITERS).
   On a few large features (~30k+ verts each) it exceeds the worker's 30s timeout; on a real
   ~12MB dataset it runs for minutes-to-hours. The synthetic 07-01 fixture only passed
   because its 43.5k verts are spread across 300 SMALL features (low per-feature V).

2. `runOptimize()`'s 30s timeout calls `settleViaSync()`, which re-runs the SAME quadratic
   `optimize()` SYNCHRONOUSLY on the MAIN THREAD without terminating the still-running worker.
   For any dataset the worker can't finish in 30s this guarantees a multi-minute main-thread
   block → UI freeze → tab OOM → crash (exactly what the UAT user hit).

Purpose: make the tool FAST on normal data and SAFE (never crashes, always settles) on
pathological/huge data, while preserving every existing Phase-7 invariant (A3 worker
boundary, always-settles, gated single modify, D-05 lossless merge, D-06 topology intent,
D-07 best-effort, no auto-export).

Output:
- A bounded, near-linear `optimize()` (cheap-search simplify + capped/once topology validation).
- A safe `runOptimize()` timeout path (terminate worker + reject with a relayable error; the
  small-input sync path stays for tests/SSR).
- A regression test (`optimize.perf.test.ts`) proving a few-large-features dataset (~100k+
  verts) completes under a hard time bound OR returns a graceful over-budget result — not a hang.
</objective>
