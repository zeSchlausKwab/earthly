<objective>
Add live MCP hot-reload (D-05): the registry actively PULLS tools from the connected ContextVM MCP client via poll-based `client.listTools()` and registers them as `kind:'remote-mcp'` (origin = `EarthlyGeoServerClient.SERVER_PUBKEY`), so the advertised tool list (D-04) stays in sync with the server's manifest — replacing the 14 hand-transcribed MCP tools hardcoded in `definitions.ts`.

This is the riskiest, LAST, ISOLABLE, DEFERRABLE wave. Two hard constraints from research:
1. **Assumption A1 is UNVERIFIED:** the MCP client SDK exposes `listTools()`, but whether the live Earthly geo server (pubkey `ceadb7d5…`) actually implements the `tools/list` MCP method has NOT been network-tested. → This plan OPENS with a `checkpoint:human-verify` spike calling `listTools()` against the live server. If unsupported, the human approves the fallback (keep the hardcoded list) and the rest of the wave is DROPPED — INFRA-01/02/03 + TOOLS-01 are already complete in Plans 01-05 and unaffected.
2. **Push notifications are a mirage over the stateless transport (Pitfall 3):** `EarthlyGeoServerClient` runs `isStateless: true`, so `initialize` is emulated locally and server-initiated `notifications/tools/list_changed` is not guaranteed. → Implement POLL-based refresh (init + manual refresh + interval), NOT `setNotificationHandler` push. Document push as a future optimization once a stateful transport is confirmed.

Purpose: Complete D-05's in-scope hot-reload as a clean, droppable wave; keep the registry honest to the live server manifest.
Output: a `listTools()` passthrough on the client, the spike checkpoint, and (if green) `mcp-sync.ts` poll-based registration; (if red) documented fallback to the hardcoded list.
</objective>

<threat_model>
## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| live MCP server → registry (via listTools) | The server's tool manifest (remote, semi-trusted) is registered into the local registry; schemas/handlers cross here. |
| polled tool call → ContextVM/Nostr | Remote tool invocation leaves the host. |

## STRIDE Threat Register

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-02-17 | Spoofing | a remote server advertises tools that masquerade as local/editor tools | mitigate | All synced tools are tagged `kind:'remote-mcp'` with `origin: SERVER_PUBKEY` (D-03) so the chat/UI stays aware of their remote nature; they cannot be registered as `editor`/`authoring-primitive`. |
| T-02-18 | Denial of Service | `listTools()` hangs/errors over the stateless Nostr transport → registry stalls | mitigate | Poll-based with graceful degradation to the last-known/hardcoded set on failure; no blocking push subscription (Pitfall 3). |
| T-02-19 | Tampering | trusting a malformed remote schema into the dispatch hot path | mitigate | Validate the manifest shape before registering; reuse the existing dispatch-boundary arg validation (parseToolCallArguments + clamps) for remote tool args (V5). |
| T-02-SC | Tampering | npm/pip/cargo installs | accept | No installs — `@modelcontextprotocol/sdk` + `@contextvm/sdk` already present (RESEARCH audit). |
</threat_model>
