# Phase 3 — UI Design Contract

> Visual and interaction contract for the File Ingest & Multimodal phase. Generated by gsd-ui-researcher, verified by gsd-ui-checker.
>
> Scope (from 03-CONTEXT.md): the chat-input **file-chip strip** (button + drag-and-drop, one chip per file, per-file parse status + expandable stat line) and the **vision-gate affordance** (three-tier image-send control). All new UI mounts inside `src/features/chat/ChatPanel.tsx` alongside the existing `ChatGeometryAttachment`. Map placement, geocoding, and parsing are non-visual seams (Authoring API / ingest store / tool registry) and carry no new UI beyond toast/chat-error feedback. Out of scope: binding chip, diff/preview, safety levels (Phase 5); sandbox UI (Phase 4); always-on data-grid preview (deferred per D-03 and Deferred Ideas).

## Design System

This project already ships a complete, established shadcn (new-york) design system. **Do NOT introduce new tokens, fonts, or color values for this phase.** Reuse the existing primitives and CSS variables verbatim. Source of truth: `styles/globals.css`, `components.json`, `src/components/ui/*`.

| Property | Value |
|----------|-------|
| Tool | shadcn (existing, `components.json` present) |
| Style | new-york |
| Base color | neutral |
| CSS variables | yes (`styles/globals.css`, `@theme inline`) |
| Component library | Radix UI (existing `src/components/ui/*`) |
| Icon library | lucide-react |
| Font (sans) | Poppins (`--font-sans`) |
| Font (mono) | JetBrains Mono (`--font-mono`) — for code/snippet/byte readouts only |
| Radius | `--radius: 0.2rem` |
| Utility | `cn()` from `@/lib/utils` (tailwind-merge + cva) |

**Existing components to reuse (do not rebuild):** `Button`, `Tooltip`, `Popover`, `Collapsible`, `Progress`, `Skeleton`, `Alert`, `Dialog`, `Badge`-style inline chips (see `ChatGeometryAttachment` chip pattern), `sonner` (toast). New file chips MUST follow the existing chip visual language in `ChatGeometryAttachment.tsx` (rounded border, `bg-background`, compact text, lucide icon + label + `X` clear).

## Spacing Scale

The codebase uses Tailwind v4 with `--spacing: 0.25rem` (4px base). All values are multiples of 4. Reuse Tailwind spacing utilities; do not hardcode arbitrary pixel values.

| Token | Value | Usage |
|-------|-------|-------|
| xs | 4px (`gap-1`, `p-1`) | Icon-to-label gap inside a chip |
| sm | 8px (`gap-2`, `p-2`) | Chip internal padding, gap between adjacent chips |
| md | 16px (`gap-4`, `p-4`) | Strip-to-input gap, expanded-summary padding |
| lg | 24px (`gap-6`) | Section padding within expanded summary popover |
| xl | 32px | Reserved (not expected this phase) |
| 2xl | 48px | Reserved |
| 3xl | 64px | Reserved |

**Exceptions (match existing chat conventions, already in the codebase):**
- Compact chip controls use `h-8` buttons with `gap-1.5` and `text-xs` (matches `ChatGeometryAttachment` trigger and `ChatPanel` controls).
- Icon sizing inside chips: `h-3.5 w-3.5` (lucide), matching existing chat chips.
- Drop-target affordance may use a `p-2.5` dashed-border zone (matches existing `p-2.5` panel padding).
- **Touch targets:** the file-chip remove (`X`) and the attach button must be at least `h-8` (32px) tall to remain tappable on mobile (mobile-first per CLAUDE.md); icon-only controls in the strip use `h-8 w-8`.

## Typography

Reuse the existing chat type scale (Tailwind classes already used across `ChatPanel.tsx`). Exactly 4 sizes, 2 weights. Do not introduce new sizes.

| Role | Size | Weight | Line Height | Tailwind |
|------|------|--------|-------------|----------|
| Display / section heading | 16px | 600 (semibold) | 1.2 (`tracking-tight`) | `text-base font-semibold` |
| Body / chip label | 14px | 400 (regular) | 1.5 | `text-sm` |
| Label / chip filename + control text | 12px | 500 (medium) | 1.4 | `text-xs font-medium` |
| Caption / parse stat line + status | 11px | 400 (regular) | 1.4 | `text-[11px] text-muted-foreground` |

**Weights:** regular (400) and semibold (600) are the contract pair; medium (500) is permitted ONLY for the existing `text-xs font-medium` control-label idiom already pervasive in chat UI (e.g. `ChatPanel.tsx:431`). No other weights.

- Byte sizes, row×column counts, and dimensions render in caption size; numeric/byte readouts may use `font-mono` (`--font-mono`, JetBrains Mono) for alignment, matching the existing code-block idiom (`ChatPanel.tsx:1336`).
- The expandable summary heading (when expanded) uses the Label role (`text-xs font-medium uppercase tracking-wide text-muted-foreground`), matching the existing section-label idiom (`ChatPanel.tsx:555`).

## Color

Reuse existing semantic CSS variables only. No new hex values. The 60/30/10 split maps to the existing token roles.

| Role | Token | Usage |
|------|-------|-------|
| Dominant (60%) | `--background` / `bg-background` | Chat panel surface, chip background, drop-zone fill |
| Secondary (30%) | `--muted` / `bg-muted`, `--card` | Chip hover, expanded-summary surface, idle/secondary chip states |
| Accent (10%) | `--primary` / `bg-primary` | See reserved list below |
| Destructive | `--destructive` | Vision hard-disabled tooltip emphasis, parse-failure status text/icon, remove-on-error |
| Uncertain / warning | existing amber idiom (`text-amber-600 dark:text-amber-400`, `bg-amber-50 dark:bg-amber-950`) | Vision **unconfirmed** badge + opt-in warning, already used in `ChatPanel.tsx:549,620` |

**Accent (`--primary`) reserved for — explicit list (nothing else):**
1. The active/primary state of the **attach-file** trigger button when the file picker is open (matches `ChatGeometryAttachment` `variant="default"` active idiom).
2. The **send / send-anyway** confirm action button.
3. The **"Map these rows"** primary CTA when a parsed tabular/GeoJSON chip offers placement.

**Status color mapping for the file chip (the one place color carries meaning):**
| Parse status | Visual |
|--------------|--------|
| Parsing | `Progress` bar or spinner, caption in `text-muted-foreground` |
| Parsed (success) | caption in `text-foreground`; no accent (neutral success, matches existing "attached" chip) |
| Failed | icon + caption in `text-destructive` |
| Image — vision confirmed | normal chip, send enabled |
| Image — vision unconfirmed | amber warning badge on chip + on send affordance |
| Image — vision unsupported | chip rendered muted/dimmed (`opacity-60`) with a hard-disabled tooltip |

## Copywriting Contract

Copy is sentence-case, concise, verb-first for actions (matches existing chat tone). Filenames are shown verbatim and truncated with `truncate`.

| Element | Copy |
|---------|------|
| Attach-file trigger (button label/tooltip) | `Attach file` |
| Drop-zone hint (drag-over state) | `Drop files to attach` |
| Drop-zone idle hint (if shown) | `Drag files here or click to attach` |
| Primary CTA (placement) | `Map these rows` (tabular) / `Add to map` (GeoJSON) |
| Send with unconfirmed vision (opt-in confirm) | `Send anyway` |
| Empty state heading (no files attached) | *(none — strip is absent until a file is attached; no empty placeholder, matching the geometry-attachment pattern)* |
| Empty state body | *(n/a — see above)* |
| Parse summary (tabular) | `{rows} rows × {cols} columns · {n} coordinate column(s) detected` |
| Parse summary (GeoJSON) | `{n} features · {types} · bbox detected` |
| Parse summary (text) | `{lines} lines · {chars} characters` |
| Parse summary (image) | `{filename} · {w}×{h}` |
| Parse summary (wide-table cap) | append `· …{N} more columns` |
| Error state — parse failed | `Couldn't parse {filename}. Check the file format and try again.` |
| Error state — file too large | `{filename} is too large to ingest. Try a smaller file or split it.` |
| Error state — geocode partial failure | `Located {n} of {total} rows. {failed} couldn't be geocoded.` |
| Vision tooltip — confirmed-no-vision (hard-disabled) | `{model} doesn't support images, so they can't be sent.` |
| Vision badge/tooltip — unconfirmed | `This model may not support images. Send anyway?` |

**Destructive actions in this phase:**
| Action | Confirmation approach |
|--------|----------------------|
| Remove an attached file chip (`X`) | No modal — immediate, low-stakes (re-attachable); the chip simply disappears, matching the existing attachment `Clear` behavior. Session-only data per D-12, so removal is non-destructive to persisted state. |
| Send image to an **unconfirmed-vision** model | Inline opt-in confirm (button text `Send anyway`, amber warning), NOT a blocking modal — per D-08 three-tier gate. This is the only confirm-gated action in the phase. |

There is no irreversible/destructive data operation in Phase 3 — parsed data is in-memory and session-only, placement is additive through the Authoring API, and publishing remains a separate explicit user action (out of scope here).

The vetting gate is therefore not triggered (no third-party block enters this contract).

| Registry | Blocks Used | Safety Gate |
|----------|-------------|-------------|

## Interaction Contract Notes (for planner + executor)

These are interaction specifics derived from CONTEXT.md decisions, captured so the executor implements consistent behavior:

- **One chip per file (D-10).** The file-chip strip is a NEW component mounted alongside `ChatGeometryAttachment` in `ChatPanel.tsx`; do not fold the two together. Chips wrap (`flex-wrap`) in the input area above the textarea, matching the existing attachment row layout.
- **Two attach paths (INGEST-01).** A button (`Attach file`, lucide `Paperclip`) AND drag-and-drop onto the chat input region. Drag-over shows the `Drop files to attach` affordance (dashed border, `bg-muted`).
- **Per-chip parse status (D-03).** Each chip shows: type icon (lucide — `FileSpreadsheet` csv/xlsx, `Braces` json/geojson, `FileText` text, `Image` image), truncated filename, a compact stat line, and an `X` remove control. Parsing shows `Progress`/spinner; off-thread parse must never block the UI (INGEST-02).
- **Expandable summary (D-03).** The compact stat line expands via `Collapsible`/`Popover` for the fuller per-type summary. **No always-on data grid** (deferred per D-03).
- **Vision gate is one affordance (D-08/D-09).** A single control governs both user-attached images and the `capture_map_snapshot` one-shot flow. Three states: enabled (confirmed), amber-uncertain + `Send anyway` opt-in (unconfirmed), hard-disabled + tooltip (confirmed-no-vision). Never silently send an image to a blind model.
- **Accessibility:** disabled vision control must expose the reason via `Tooltip` (not just visual dimming); status changes (parse done/failed) should be announced politely (toast via `sonner` is acceptable). Respect `prefers-reduced-motion` (already globally handled in `index.css`) — no spinner-only status; pair with text.
