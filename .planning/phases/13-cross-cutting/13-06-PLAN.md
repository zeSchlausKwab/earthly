<objective>
Close UAT test 5b (`status: failed`, severity major) — the add-to-map-stack
PHANTOM entry: clicking "Add to map stack" on a beacon that lives OUTSIDE
live-discovery fires a success toast but the beacon never renders and the Map
Stack panel stays "0/0 visible / No map stack entries."

Root cause (UAT test 5b, authoritative). Both the Plan-04 expiry-sweep effect
(`GeoEditorView.tsx` ~L1311-1333) AND the Plan-03 `deriveVisibleEntitiesFromStack`
render gate resolve individual beacon stack entries against
`beaconLookupSuperset` (= the `#t:['live']` discovery `beacons` set ∪
`routedBeacons`). `routedBeacons` is populated ONLY when `route.focusType ===
'beacon'` (a `/beacon/:naddr` deep link). A beacon reached WITHOUT routing — an
own/link-only beacon opened via `setViewBeacon(publisher.liveBeacon)`
(`useBeaconController.ts:142`) or `handleInspectBeacon` (`useBeaconController.ts:183`)
that bypasses `navigateTo('beacon', naddr)`, or a beacon that has dropped out of
the live-discovery window — is in NEITHER set, so it is out-of-superset. The
sequence: `addBeaconToMapStack(beacon, 'manual')` (`GeoEditorView.tsx:598`) adds
the entry and fires the toast UNCONDITIONALLY; on the next render tick the sweep
resolves the entry against `beaconLookupSuperset`, finds it unresolvable
(`!resolved`), and calls `removeMapStackEntry(id)` → the entry vanishes. The
render gate independently can't resolve it either → never draws. Two reinforcing
failures.

DECISIVE property (per the debug session): out-of-superset (no `t:live` AND not
routed), NOT strictly "stale" — a stale-but-not-expired beacon still lives in the
discovery `beacons` set and resolves fine; an own/link-only beacon reproduces the
phantom too.

Purpose: a user-EXPLICITLY-added stack entry must stay resolvable + rendered even
when the entity is outside live-discovery, so "on the stack = visible" holds for
a manually-added beacon the same way it does for a deep-linked one — WITHOUT
forcing the beacon into public discovery (the D-05 throwaway-key / link-only
privacy invariant).
Output: a resolution path for explicitly-added out-of-discovery entities + a
sweep that no longer evicts them for merely leaving discovery + an honest toast.
</objective>

## Trust Boundaries

| Boundary | Description |
|----------|-------------|
| own/link-only beacon → Map Stack individual entry | An out-of-discovery beacon (no `t:live`, throwaway/own pubkey) is rendered on the map via an explicit individual stack entry, resolved from a client-local added-entity cache. |
| individual stack entry → aggregate `beacon-layer` seed | The individual-pin resolution path and the aggregate-layer seed share `deriveVisibleEntitiesFromStack`; the aggregate seed MUST stay discovery-only. |

| Threat ID | Category | Component | Disposition | Mitigation Plan |
|-----------|----------|-----------|-------------|-----------------|
| T-13-06-01 | Information Disclosure | out-of-discovery beacon leaking into public discovery | mitigate | The fix renders an added out-of-discovery beacon via the INDIVIDUAL-pin path (a client-local resolved-entity cache fed to `deriveVisibleEntitiesFromStack`'s `individualLookupSet`), NOT by tagging it into `#t:['live']` discovery. The aggregate `beacon-layer` branch of the helper still seeds ONLY from `subscriptionSet` (discovery `beacons`) — verified by acceptance criterion and by leaving the helper body + `useBeacons` filter untouched. A link-only/own beacon renders only for the user who explicitly added it; it is never published into or surfaced through public discovery. This is the D-05 (Phase 12) / T-13-03-GPSREGRESS privacy invariant, preserved. |
| T-13-06-02 | Information Disclosure | new targeted subscription widening data exposure | accept | This plan does NOT open any new network subscription (option (b) from the UAT `missing:` was considered and NOT chosen — the resolved-entity cache + sweep-guard cover the case without new network traffic). The beacon object was ALREADY resolved locally at inspect/add time (it is what the view panel is displaying); caching it exposes nothing new. No new relay filter, no new authors/#d query. |
| T-13-06-03 | Tampering | expiry-sweep decision on a user-added entry | mitigate | The sweep still evicts genuinely NIP-40-EXPIRED entities (`isExpired(resolved.event, now)`, D-02 honesty preserved — a truly-ended beacon never lingers as a stale marker). The ONLY relaxation is: a not-yet-expired entry that faded from live-discovery is no longer evicted on membership grounds. STALE (beaconState 120s) is explicitly NOT treated as expired, so the sweep cannot be tricked into either evicting a live-but-stale entry or retaining an expired one. |
| T-13-06-SC | Tampering | npm/pip/cargo installs | mitigate | No new packages installed (edits to one existing file + its existing test). No slopcheck checkpoint needed. |

Note: option (b) from the UAT `missing:` (open a targeted subscription for an
added out-of-discovery beacon) is deliberately NOT taken — it would add network
surface for no benefit, since the beacon object is already in hand at add time.
The cache + sweep-guard approach (options a + c + d) is strictly lower-surface.
