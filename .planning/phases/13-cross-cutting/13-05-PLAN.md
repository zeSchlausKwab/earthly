<objective>
Close UAT tests 2 and 3 (both `status: failed`, severity major) — the two beacon
deep-link failures that share ONE emit-side root cause, plus the independent
tour sub-symptom behind test 2.

This is the WR-01 deferred item finally being fixed.

Two independent defects, both landing a fresh beacon-share recipient in the wrong
place:

1. **Doubled-prefix share URL (tests 2 + 3).** `BeaconViewPanel.handleCopyShareLink`
   (~L177-197, the hand-built string at ~L191) is a SECOND, legacy beacon-share
   emitter that bypasses the canonical `buildSharePath`/`getEntitySharePath`
   pipeline every other kind uses. It emits `${origin}/#/beacons/beacon/${naddr}` —
   a legacy `#/` hash form with the plural sidebar-view segment `beacons/` doubled
   in front of the singular share segment `beacon/`. Only the singular `beacon` is
   a `SHARE_ROUTES` key; the leading `beacons` forces `parsePathSegments` down the
   sidebar-tail branch → `sidebarView:'beacons'` (the LIST) instead of matching
   `SHARE_ROUTES.beacon`. Fixing the emitter to the clean single-prefix
   `/beacon/${naddr}` (what the canonical `handleShare` produces via
   `new URL('/beacon/naddr', origin)`) resolves BOTH tests at once, because for a
   comment the same 2-segment base yields `/beacon/${naddr}/comment/${id}`.

2. **Route-blind tour auto-start (test 2 sub-symptom).** `TourManager` (mounted
   unconditionally in `src/App.tsx:15`) auto-starts the driver.js tour 800ms after
   mount gated ONLY on `!hasSeenTour`. It never inspects the URL, so a fresh
   deep-link land in a never-toured browser shows the welcome tour over the shared
   entity. This is INDEPENDENT of defect 1 — fixing the URL does not stop the tour.

Purpose: a shared beacon link opens exactly the shared entity (inspect panel +
optional comment focus) with no onboarding interruption, matching the behavior
UAT already confirmed for the other four kinds (test 4 passed).
Output: a corrected clean-path share emitter + a deep-link suppression guard.
</objective>
