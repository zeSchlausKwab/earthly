<objective>
Land the user-visible and integration half of the safe-editing gate: the always-visible binding chip (SAFE-01), the inline Apply/Cancel diff block (SAFE-03), the "Just accept" auto-accept toggle (SAFE-04 / D-12), and the chat-loop wiring that connects Plan 04's `createAuthoringGate` to the live tool path so the gate actually fires, renders, and applies.

Purpose: Plans 01–04 built every host-side MECHANISM (classification, snapshot/undo, persisted safety level + binding resolver, the async buffer-then-apply gate) but deliberately left them headlessly testable against injectable callbacks — Plan 04 states verbatim "The Apply/Cancel UI and chat-loop wiring land in Plan 05" and "in Plan 05 this is wired to the disclosure buttons." This plan supplies that UI + wiring so the phase's two visible success criteria become true: (1) a chip always shows the bound target and no mutation fires without a shown binding; (2) the user previews add/modify/delete before applying. The chip reads the Plan-03 `resolveBinding`; the diff block clones `CodeRunDisclosure` and adds inline Apply/Cancel (D-04/D-05/D-08); the toggle flips the Plan-03 persisted `safetyLevel` to 3 via `setSafetyLevel` (D-12); the wiring constructs `createAuthoringGate(editor, { getSafetyLevel, emitDiffBlock, requestConfirm })` on the async tool loop (store.ts) and the run_code recorded-batch path, pushing a `DatasetDiffDisclosure` into the transcript and resolving the gate's awaited confirm when the user clicks Apply/Cancel. The real apply continues to route through `createAuthoring` → `runInterceptors` (no bypass), one tool call / recorded batch = one diff = one apply = one snapshot = one undo (D-11), with an "Undo last AI edit" affordance near the applied block (SAFE-06 surface; the snapshot mechanism itself is Plan 02).

Output: `BindingChip.tsx` (chip + "Just accept" toggle), `DatasetDiffDisclosure.tsx` (inline diff + Apply/Cancel), a `pendingDiffStore.ts` bridge that turns the gate's `emitDiffBlock`/`requestConfirm` deps into a transcript-rendered block with an awaitable resolver, and the `store.ts` / `runCode.ts` / `execute.ts` wiring that constructs and awaits the gate on the AI mutation path.

Depends on Plan 03 (`resolveBinding`, `safetyLevel` + `setSafetyLevel`) and Plan 04 (`createAuthoringGate(editor, { getSafetyLevel, emitDiffBlock, requestConfirm })`). It shares `store.ts` with Plan 03, so it is sequenced to Wave 3 (after 03's `ChatSettingsSnapshot`/`setSafetyLevel` change lands) and after Plan 04's gate exists.
</objective>
